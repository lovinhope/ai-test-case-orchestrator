# Commit manual cases

Read [case-schema.md](references/case-schema.md), [test-data-contract.md](references/test-data-contract.md), and the parent [interaction-contract.md](../references/interaction-contract.md), including their test-case quality rules, the matching test points, association, and challenge artifacts. Run `scripts/generate_test_cases.py` to verify commit identity and that points are confirmed. Before cases, query and read the configured historical manual-case/defect knowledge base and write `04-historical-case-association.md`.

When a case needs concrete records, use the test-database workflow in `test-data-contract.md`: read the local test-database configuration, verify the target is non-production, inspect reference data, prepare a run-scoped data plan, and—only when the current request explicitly authorizes creation—write and verify data through the configured Lowrisk data-mock adapter or a reviewed database adapter. Persist `04-test-data-manifest.md`, link each dataset to its case number, and include the manifest in the case preconditions. If creation cannot be verified, keep the dataset `待准备` and do not claim the case is executable.

Before drafting a case, explicitly decide whether it requires test data. For every case that exercises a database-backed rule, data refresh, cache, API request, order, position, valuation, permission, page query, or cross-table consistency, derive the required data set from the project implementation—not from the requirement text alone. Read the changed code and its call chain to identify the actual entry point, tables/entities, joins, filters, caches, enums, status transitions, dates, tenant/company/product scope, and upstream/downstream records that affect the expected result. Inspect the project schema, mapper/SQL, DTOs, configuration, reference data, and existing fixtures where available; use the smallest complete dataset that reaches the code path, including control records for non-hit/allow branches and all records needed for pre-trade, post-trade, real-time, historical, or page-display assertions. Reuse one verified dataset across cases when the parameters and required state are identical; do not create duplicate datasets merely because cases are different. Never invent product codes, stock types, statuses, enum values, table fields, or foreign keys. If the code or environment cannot verify a required value or table, record the uncertainty/blocker and leave the dataset `待准备` rather than substituting placeholders or claiming successful creation.

Then write candidate `04-test-cases.md`; every case is `pending_human_review`, traceable to a point and the single commit, and includes a linked task/requirement URL, requirement explanation, unique number, purpose, priority, test point, coverage type, complete preconditions, explicit test data/source/cleanup, deterministic numbered steps, one-to-one matching expected results, post-processing, and a `测试结果：待执行` placeholder. Apply the quality gate in `case-schema.md` before presenting cases for human review. The reviewer-facing page must provide editable review inputs and a submit-case-review action that records adopted, modified, or discarded per-case decisions. Do not mark cases adopted automatically.

When the requester asks to push cases to Confluence, use `scripts/publish_test_cases.py` only after local validation passes. The script reads the push destination from `test-case-publish.ini` in this skill directory (or `--config`), reads the Confluence PAT from the existing user-level `TASKFLOW_CONFIG_PATH` configuration, and never stores or prints credentials. The configured destination must identify a Confluence parent page/path; do not assume the standards page is the publication destination. Before any write, validate every selected case against the configured standards and format pages: traceability, unique number/title, priority, test point, coverage type, complete preconditions, explicit test data/source/cleanup, deterministic numbered steps, one-to-one objective expected results, post-processing, test result placeholder, repeatability, and non-duplicate title. Exclude discarded cases. Candidate cases must remain visibly marked as candidates/drafts and must not be represented as adopted cases. Use `--dry-run` to preview the destination, validation summary, and rendered page; only an explicit non-dry-run invocation may create the Confluence page. The script must fail closed when the destination, credentials, case fields, step/result counts, or required evidence are missing.

Example: `python scripts/publish_test_cases.py --cases <case-dir>/04-test-cases.md --dry-run`; after review and with `publish.parent_page` configured, omit `--dry-run` to create the child page.

If points are pending, stop. If evidence is unavailable, record the block; do not invent expected results.
