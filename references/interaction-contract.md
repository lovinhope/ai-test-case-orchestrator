# Human-review interaction contract

人工评审只在 Codex 会话中进行，不生成 HTML、CSS、JavaScript、模板、评审网页或浏览器桥接代码。Markdown 审计产物是唯一权威记录。

## 通用规则

- 证据必须在会话中展示标题、摘要、来源类型、更新时间（如有）、来源链接和关联理由；不得只展示内部 ID、提交 SHA 或文件路径。
- 使用人类可读编号：证据 E01、问题 Q01、测试点 TP01、测试用例 TC01；内部 ID 仅用于 Markdown 追踪。
- 每个阶段都必须明确列出待确认项、证据、判断依据和建议处置。
- 用户必须明确确认、修改或拒绝后，才能写入对应评审结果并进入下一阶段。
- 未确认的发现、测试点和测试用例必须保持“待评审/候选”，不得自动采用。
- 已确认或已废弃的质疑点、测试点和测试用例属于不可变历史状态。重新生成必须创建新的版本/生成批次并引用原记录，不得覆盖原文件、复用原编号改变含义，或回写原始状态图。

## 产品/代码对抗

在会话中先展示业务、技术和已验证代码证据，再逐项列出 Q01、Q02 等问题。每项记录证据、来源、理由、处置和用户反馈；用户确认后写入 `02-review.md`。未解决冲突保持 `awaiting_confirmation`，不得绕过人工门禁。

## 测试点评审

展示每个 TP 编号、业务规则或流程、设计方法、预期可观察结果、优先级和追溯来源。允许用户补充、修改或新增测试点；确认后写入 `03-test-points.md`，新增或修改项在确认前保持待评审。

## 测试用例评审

展示关联 Jira/需求链接、需求说明、TC 编号、目的、前置条件、编号步骤、每步对应的一个预期结果和优先级。逐条取得“采用、修改或废弃”决定，写入 `05-case-human-review.md`；生成的用例始终先标记为候选。
